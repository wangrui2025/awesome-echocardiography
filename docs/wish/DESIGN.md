# 当前愿望的设计解释

这份文件只解释当前 Awesome Echocardiography 愿望怎样推导成本站自己的信息架构和内容选择。通用 UI、部署、Git/CI、事故历史和具体论文事实继续由现有 owner 负责。

## L0 — 中心愿望

网站的价值不在于“收了多少篇”，而在于降低研究者进入这个领域、寻找可信资源和统一评估语义时的成本。

一个条目存在于网站里，应该因为它帮助研究者回答真实问题，而不是因为它能让目录显得更大。

## L1 — 研究者真实会遇到什么情境

### 1. 第一次进入 AI Echocardiography

读者需要先知道这个领域有哪些主要任务、代表性工作、常用数据和评估方法，而不是直接面对一个无限论文清单。

### 2. 我找到一篇论文，想知道代码到底能不能用

网站必须区分：

- paper；
- project page；
- repository；
- actual implementation；
- placeholder / coming soon；
- no public code。

不能因为有 GitHub 链接就写“有代码”。

### 3. 我准备复现或比较方法

这时真正重要的是数据集、指标定义、单位、aggregation、empty case、threshold、clinical agreement 等语义是否一致。

因此 metrics 不是附属页面，而是这个资源站的重要基础设施。

### 4. 我想找更多相关工作

收录应逐步扩展，但扩展规则是“相关 + 核验”，不是“搜索到了就加入”。

没有公开代码不自动排除一篇重要论文；同样，有一个仓库也不自动证明实现已经发布。

### 5. 我想贡献新条目

贡献流程应要求把论文、项目页、代码仓库和代码状态分别提供证据，减少未来维护者重新猜测。

## L2 — 网站应该怎样回应

### 首页负责建立方向，不负责穷举

首页应给第一次访问者一个小而可信的入口：

- 这个站关注什么；
- 几篇真正有代表性的 featured work；
- 数据集和 metrics 从哪里进入；
- 怎样看更多论文。

Featured 的目的只是 orientation，不代表本站认为只有这些论文重要，也不应因为其中包含维护者自己的工作就让整个站围绕它们组织。

### Papers 是 curated catalog

论文目录可以比首页更广，但每个条目应有一致、可核验的字段和代码状态。

不要把“项目主页仓库”和“真正代码仓库”折叠成一个 Code 字段。

### Datasets 是可使用的研究入口

数据集页不仅列名字，也应该帮助研究者理解任务、数据规模、官方入口、论文、许可/访问条件和与评估的关系。

### Metrics 是可执行语义标准

指标解释顺序应服务复现：

```text
它测什么
→ 数学定义
→ 推荐实现
→ 单位 / aggregation / edge case
→ 为什么这样定义
```

CPU Reference Metrics 是语义 authority；GPU/加速实现只能证明等价，不能因为更快就重新定义指标。

### Contribution 把核验前移

提交新论文时就区分 project page、code repo 和 release status，避免 curator 后期凭仓库名字猜。

## L3 — 信息架构角色

### Home

角色：可信的领域入口。少量 featured 内容 + Papers / Datasets / Metrics 的清楚入口。

### Papers

角色：经过核验的研究目录。可以增长，但不追求形式上的“全收录”。

### Datasets

角色：把数据集从一个链接变成研究者可以实际进入的资源。

### Metrics

角色：跨论文和实现保持评估语义一致，提供数学解释和 executable reference。

### Contributing

角色：把“如何证明一个条目应该怎样标记”写成明确合同。

## L4 — 当收录或页面设计拿不准时

优先问：

1. 这会不会帮助研究者更快找到可信资源？
2. 这个链接到底证明了 project page、repo，还是实际代码发布？
3. 当前标签是否比原始证据说得更强？
4. 加入这个条目是因为它真正相关，还是只是为了让列表更长？
5. 指标规则是否对整个领域中立，还是被某篇本站熟悉的论文牵着走？
6. 第一次进入的人能否先建立领域地图，再进入长列表？

## 不属于这份文件的内容

具体论文是否已发布代码、某个指标测试值、CI/provider 配置、某次 PR 事故、CSS 实现、通用无障碍规范等不属于愿望设计解释；它们继续由 CONTRIBUTING、src/papers.ts、reference metrics、工程配置和历史记录负责。
